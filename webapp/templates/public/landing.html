Take-home results are usually read, not run

A candidate sends a notebook and a score. A senior engineer reads the code, rarely runs it, and has no data the candidate did not have. The mistakes that inflate a score do not crash anything, so they are easy to miss.

How it works

Four steps, every submission

No AI model grades the candidate. Every score comes from running their code and measuring what it does.

Read the full method

The candidate submits in a fixed format

Code, pinned requirements, and a short decision log with the score they claim. A pre-flight check on a small sample catches format problems before they submit.

We re-run it from scratch, four times

In a fresh gVisor sandbox with the internet blocked: their seed twice to test determinism, then two other seeds to test luck.

The model meets customers it has never seen

It predicts a holdout set. The answers stay outside the sandbox and the predictions are scored there, then compared with the claim.

We show where it leaked, and a person decides

A runtime trace and controlled re-runs point to the cause, with file and line. A named reviewer confirms or overrides, with a reason kept in the audit log.

The report

Six scores, each backed by evidence

Every deduction points to a finding. The weights are published in every report, and the recommendation is advice to a person, never a decision.

What it catches

The mistakes that make a model look better than it is

A field from the future

A column filled in after the outcome. The ablation re-run sets it to its real value at prediction time and measures how far the score falls.

The same customer in training and test

A random row split over repeated customers. The report compares the candidate's own score on seen and unseen customers, with a confidence interval.

Choosing the model on the test set

The trace counts how many times one test split was scored and whether the reported number was picked from those scores.

Preprocessing before the split

A scaler or imputer fitted on every row, test rows included, caught from the order of fits and splits at runtime.

A score that does not come back

A claim the code does not reproduce, or randomness that changes the result between two runs with the same seed.

Code that only works on the author's laptop

Hidden local files, packages missing from the requirements, and calls to the internet, all blocked and reported.

Fair to candidates

Evidence for a person, never an automatic rejection

Hiring decisions about people need a human in the loop. PipelineProof is built around that:

  • Every recommendation needs a named reviewer to confirm or override it, with a written reason.
  • Candidates are told how their work is assessed before they start.
  • After review, candidates can see the evidence about their own work and contest it.
  • Every action is kept in an audit log; personal data is deleted after a set retention period.

How it works

From a zip file to evidence a reviewer can act on

PipelineProof treats a take-home like a scientific claim: it re-runs the experiment under controlled conditions, tests the result on data the candidate never had, and looks for the reasons a result might not hold up.

1. A fixed submission format

To re-run anyone's work without a person working out how, every submission follows the same small contract:

  • pipeline.toml names the Python version and the commands that train and predict.
  • requirements.txt pins every package to an exact version.
  • Training reads the data folder and the seed from environment variables and writes the model and its own validation score.
  • Prediction reads unseen rows and writes one probability per row.
  • DECISIONS.md states the claimed score, the seed, the validation approach and any AI tools used.

Candidates get a starter template that already follows it, and a pre-flight check on a 400-row sample tells them about problems before they submit. The pre-flight never touches the holdout and never reveals a score.

2. Re-run, four times

Each run happens in a fresh sandbox built from the candidate's own pinned requirements. The sandbox has no internet access, capped CPU, memory and time, and is destroyed afterwards.

  • Declared seed: does the claimed number come back?
  • Declared seed again: is the pipeline deterministic, or does unseeded randomness change the answer?
  • Seeds 101 and 202: how much of the result is luck?

Imports are checked against the declared requirements, and any attempt to reach the network or read a file that was not submitted is recorded.

3. Customers the model has never seen

Each task has a holdout: rows from entities that are not in the training data, in the state they would be in at prediction time. The model predicts them inside the sandbox; the answers stay outside and the predictions are scored there.

The gap between the claimed score and the holdout score is the single most useful number in the report. It needs no knowledge of how the code works, so it catches problems the other checks miss.

4. Where it leaked

While the code runs, a tracer records every data split, every model or preprocessing fit, and every metric call, with the rows involved. That shows when test rows reached a fit, when preprocessing was fitted before the split, and when one test set was scored again and again to pick a model.

For suspicious columns, PipelineProof re-runs the pipeline with the column set to its real value at prediction time. If the candidate's own score falls, the column was carrying information it should not have. That is an experiment, not a guess.

What PipelineProof does not do

  • It does not reject anyone. Every recommendation goes to a named reviewer who confirms or overrides it.
  • It does not use an AI model to grade code or write scores.
  • It does not judge style. It measures whether the claimed result holds up and why.
  • It does not keep data forever: personal data is deleted after the retention period set by the employer.

Current scope

  • Tabular tasks on CPU, in Python 3.11 to 3.13.
  • Runtime tracing for scikit-learn, and for XGBoost and LightGBM through their scikit-learn interfaces; scripts and notebooks.
  • One task in the library today (broadband churn), with planted traps, a holdout and a brief.
  • Scoring rubric v1 with hand-set, published weights.
